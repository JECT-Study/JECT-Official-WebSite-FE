# branch

할 작업 설명(필수)과 이슈번호(선택)를 받아, 저장소 컨벤션에 맞는 브랜치를 만든다. 핵심은 작업 내용에서 적절한 type과 짧은 영어 kebab 이름을 정하고, 최신 `dev`를 기준으로 브랜치를 생성하는 것이다.

## 브랜치 이름 형식

```
<type>/<이슈번호>-<추천이름>      # 이슈번호가 있을 때  예: feat/123-faq-migration
<type>/<추천이름>                 # 이슈번호가 없을 때  예: feat/faq-migration
```

- **type**: 작업 성격에서 추론한다. `feat`(기능) / `fix`(버그) / `refactor` / `chore` / `docs` / `style` / `test` / `build` / `ci` / `perf`. 커밋 컨벤션의 prefix와 동일한 집합.
- **추천이름**: 작업 내용을 압축한 영어 kebab-case. 소문자, 단어 2~4개, 특수문자 없이 하이픈으로만 연결.
  - 예: "FAQ 페이지 마이그레이션"은 `faq-migration`, "지원 퍼널 E2E 추가"는 `apply-funnel-e2e`, "레거시 리다이렉트 정리"는 `legacy-redirects`.
- **이슈번호**: 사용자가 주면 type 뒤, 이름 앞에 숫자만 넣는다(`#`나 `issue` 같은 접두어 없이). 안 주면 생략하며, 억지로 만들지 않는다.

## 작업 순서

1. **입력 확인**: 작업 설명이 있는지 본다. 없으면 무슨 작업을 할 브랜치인지 묻는다. 이슈번호는 선택이므로 없으면 생략한다.
2. **이름 생성**: 위 형식으로 후보 이름을 만든다. type 추론이 애매하거나 이름이 여러 갈래로 가능하면, 만들기 전에 후보를 한 줄로 제시해 확인받는다. 명확하면 바로 만든다.
3. **base 최신화**: 브랜치는 최신 `dev`에서 분기한다.
   - 작업 트리에 커밋 안 된 변경이 있으면 먼저 알린다(브랜치를 바꾸면 그대로 따라온다).
   - 깨끗하면: `git checkout dev && git pull --ff-only && git checkout -b <이름>`.
   - 현재 브랜치 기준으로 분기해야 한다면 사용자 의도를 확인한 뒤 현재 HEAD에서 `git checkout -b <이름>`.
4. **중복 확인**: 같은 이름의 브랜치가 이미 있으면 새로 만들지 말고 알린다(`git branch --list`, 원격은 `git ls-remote --heads origin <이름>`).
5. **결과 보고**: 생성한 브랜치명과 base를 알린다.

## 주의

- 어떤 브랜치에서든 작업이 섞이지 않도록 새 작업은 `dev` 기준으로 분기하는 것을 기본으로 한다.
- `main`은 운영 배포용이므로 작업 브랜치의 기준으로 쓰지 않는다.
- 브랜치 이동으로 lockfile이 바뀌면 post-checkout 훅이 `pnpm install`을 자동 실행할 수 있으며, 정상 동작이다.
- 브랜치명에 한글/공백/대문자를 넣지 않는다. 항상 영어 kebab-case.
